Memory That Doesn't Reach Everywhere Isn't Memory

Adding conversation history to the final answer prompt felt like the whole fix. It wasn't — and figuring out why taught me more about agent architecture than the fix itself.

Once tool-calling was working — the agent could choose between semantic search, exact keyword search, and file listing — the obvious next step was memory. Without it, every question was independent: no "tell me more," no "what about X," nothing that resembled an actual conversation.

The first attempt

The fix looked simple: keep a running list of past question/answer pairs, and inject the last few turns into the final prompt before generating an answer. I tested it with a natural follow-up:

  • You: "what is the purpose of this project"
  • Agent: (accurate answer about the AI interview platform)
  • You: "which file handles that?"

The agent answered with total confidence: app/auth/sign-in/[...sign-in]/page.jsx. Completely wrong — that's the sign-in page, unrelated to interview feedback.

Finding the actual gap

The history was in the final prompt. So why did it fail? Because by the time history reached the model, the damage was already done. My agent doesn't go straight from question to answer — it first asks the model to choose a tool and generate a search query. That routing step ran before the final prompt, and it had zero access to conversation history.

So when "which file handles that?" hit the router, "that" had no referent. The router searched for the literal string "that," retrieved five semantically-nearest-but-irrelevant files, and handed them to the final prompt as if they were the answer. The history I'd added was real — it just arrived one step too late to matter.

The fix, and its limits

I passed conversation history into the tool router too, with an explicit instruction to resolve pronouns into a concrete search term before picking a tool. Result, second attempt:

  • You: "which file handles that?"
  • Agent: chose grep_exact('handle_that') — then answered "I cannot determine which file handles this without more context."

Genuinely better — a wrong-but-confident answer became an honestly-uncertain one, which is the safer failure mode. But it's not a full fix. handle_that isn't "that" resolved into a real concept; it's the model still stuck between the pronoun and a coherent search term, just further along than before.

I tried a couple more phrasings and got the same pattern: partial resolution, then a stall. At that point it stopped looking like a prompting bug and started looking like a capacity limit — turning a pronoun into a search query is a small multi-step reasoning task (identify referent → recall the relevant concept → form a query), and a 1.5B-parameter model run entirely on a laptop CPU doesn't reliably chain that many steps.

Where I landed

I documented it as a known limitation rather than chasing it further with prompt tweaks that were unlikely to fix an underlying capacity issue. Two things I'd actually try if I revisit this: routing the pronoun -resolution step through a larger model while keeping the small model for cheap, fast tool selection; or resolving obvious pronouns with a lightweight heuristic in code before the question ever reaches the model at all.

The bigger lesson generalizes past this one bug: in an agent with multiple steps, "adding memory" isn't a single change — it's a question of which specific step actually needs the context, and confirming it gets there.
