My Agent Invented Folders That Don't Exist

Debugging the first real bug in my codebase Q&A agent — a textbook RAG hallucination, and the fix that was smaller than the problem felt.

I'd just finished the first working version of my agent: a local RAG pipeline that ingests a codebase, embeds it into ChromaDB, and answers questions about it using a small model running through Ollama. First test question — "what does this project do?" — came back accurate and coherent. Good sign.

Second test broke it.

The question

I asked: "how is the app organized — list the folders and their purpose?" The agent answered confidently with ten folders: components/ui, common, features, services, utils, hooks, styles, docs, tests, entrypoints — each with a plausible-sounding description of its purpose.

The problem: my actual repo has app/, components/ui/, hooks/, lib/, public/, and utils/. Most of what the agent listed simply doesn't exist. It wasn't a vague or hedged answer either — it was confident, specific, and wrong.

Why it happened

Two things stacked on top of each other:

  • Retrieval had nothing to retrieve. My ingestion script chunked every code file into 50-line pieces, but nothing in the vector store actually described the repo's structure. When the query embedding for "list the folders" ran against the database, the closest matches were UI component files — not because they were relevant, but because they were the least-irrelevant thing available.
  • The model filled the gap from memory. A 1.5B-parameter model has seen thousands of Next.js projects during training, and services/, hooks/, and tests/ are extremely common folder names in that ecosystem. With no real structural data in its context, it reached for the statistically likely answer instead of saying "I don't know."

This is the textbook definition of a RAG hallucination: not the model "lying," but the model doing exactly what language models do — predicting plausible text — when the retrieval step failed to constrain it with real information.

The fix

The fix was smaller than I expected. Instead of trying to make the model behave better through prompting alone, I gave retrieval something real to find. During ingestion, I now walk the actual repo tree and generate a dedicated chunk — PROJECT_STRUCTURE_OVERVIEW — containing the real folder structure as text, and store it in the vector database like any other chunk.

Re-running the same question, retrieval now pulls that overview chunk alongside the UI component files, and the answer changed from ten invented folders to the actual ones — app/, components/ui, and their real subfolders like auth/ and dashboard/.

What I'd tell someone hitting this

If a RAG agent hallucinates on a category of question, check whether the vector store actually contains an answer to that category before touching the prompt. Prompting can reduce a model's willingness to guess, but it can't manufacture information that was never retrieved. The fix here wasn't "tell the model not to hallucinate" — it was "give retrieval a real document to find."
